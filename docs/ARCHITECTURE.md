# AgroBalance — архитектура MVP

React + TypeScript + Tailwind CSS + Recharts → HTTP JSON API FastAPI → SQLAlchemy → PostgreSQL 16.
Локальный демонстрационный запуск поддерживает SQLite; целевая среда — PostgreSQL в Docker Compose.

## Данные

- `users`: профиль, Argon2id-хеш пароля, признак демо.
- `sessions`: только SHA-256-хеш случайного токена, срок 7 суток; cookie HttpOnly, SameSite=Strict.
- `login_attempts`: ограничение частоты входа, регистрации, демо и смены пароля через БД.
- `crops`: личный справочник пользователя; Kc, длительности стадий, источник.
- `fields`: параметры участка и начальные условия баланса; optimistic version + блокировка строки PostgreSQL.
- `weather_data`: последний ответ Open-Meteo, источник и время загрузки.
- `balance_days`: уникальная пара участок/дата; снимок ETo, Kc, Pe и времени ввода.
- `irrigations`: планы отдельно от факта; снимки площади и эффективности на момент создания.
- `recommendations`: пересчитываемые ежедневные результаты с исходными параметрами.

Все маршруты данных проверяют владельца участка, культур и записей. Демонстрация создаёт отдельный аккаунт и три участка для каждого посетителя.

## Водный баланс

Начальный дефицит задаётся на начало `balance_start`. Для каждого дня:

1. ETc = Kc × ETo.
2. D_before = clamp(D_previous + ETc − Pe, 0, TAW).
3. Из D_before вычитается чистый слой всех выполненных поливов этой даты: V_actual / (area_snapshot × 10) × efficiency_snapshot.
4. D_after = max(0, D_before − sum(I_actual_net)).
5. RAW = p × TAW; при D_after ≥ RAW оставшаяся чистая норма = D_after − D_target; валовая норма = чистая / efficiency; объём = валовая × area × 10.

Каждый повторный расчёт заменяет данные одного дня и переигрывает последовательность от исходного дефицита. Подтверждение, исправление и удаление полива запускают тот же пересчёт; накопительного повторного списания воды нет. Сетевой повтор создания защищён уникальным `request_key`. Несколько отдельных реальных поливов за день разрешены.

Пропуск дня останавливает цепочку: приложение не придумывает значения. Прогноз до двух дней вперёд хранится как сценарий, не меняет сегодняшнее состояние. Прогноз не включает плановые поливы и не управляет оборудованием. Текущая рекомендация недоступна при отсутствии сегодняшнего непрерывного баланса или давности сегодняшних исходных данных более 6 часов.

Фактический полив применяется после ETc и Pe за сутки. Внутрисуточная последовательность не моделируется. Грунтовое питание, сток, глубокая фильтрация и водный стресс отдельно не рассчитываются. Исторические поливы до balance_start видны в аналитике, но считаются уже включёнными в начальный дефицит.

## Агрономические данные

Коэффициенты — стартовые ориентиры FAO-56, таблица 12: https://www.fao.org/4/x0490e/x0490e0b.htm.
Для пшеницы выбран вариант яровой культуры; значения конца сезона зависят от уборки. Длительности стадий — явно демонстрационные, не региональная рекомендация. Между начальной и средней стадией Kc линейно растёт, в поздней стадии линейно падает. До посадки и после расчётного сезона рекомендация не формируется.

Pe вводит пользователь для каждого дня; автоматической подстановки прогнозного дождя нет. TAW, p, эффективность, начальный и целевой дефицит заполняются пользователем. Незаполненные параметры не подменяются значениями справочника почв.

## Погода

Open-Meteo Forecast API: https://open-meteo.com/en/docs. Дневные ETo FAO, температура и влажность; максимальная скорость ветра за день (м/с), суммарные осадки (мм). Forecast horizon 3 дня, тайм-аут 8 секунд. В карточке участка данные автоматически проверяются при открытии и раз в час; запросы к API кэшируются минимум 60 секунд. Данные старше 6 часов отмечаются устаревшими. Сбой не уничтожает кэш; пользователь может вводить ETo вручную. Демо-погода всегда явно помечена учебной.

Перед коммерческим использованием проверить условия поставщика: https://open-meteo.com/en/terms. Атрибуция отображается в интерфейсе.

## Развёртывание и ограничения

Миграции Alembic выполняются до старта API. Один контейнер обслуживает собранный frontend и API, PostgreSQL хранит данные в отдельном volume. Caddy в профиле public предоставляет HTTPS. Пароли передаются через окружение; источник .env исключён из Git и Docker-контекста. Проверка Origin + SameSite-cookie защищает браузерные изменения от cross-site запросов.

Заявленная нагрузка 50 пользователей — целевой показатель, не измеренный SLA. Перед реальным пилотом нужны нагрузочный прогон, проверка агрономом и регламент резервного копирования. Ограничитель входа объединяет пользователей за одним IP; за прокси он консервативно считает IP прокси, пока оператор не настроит доверенную инфраструктуру. Для большой нагрузки нужен централизованный limiter с атомарными счётчиками. Демо-аккаунты сохраняются в БД; на публичном сервере отключите демо или настройте очистку старых тестовых аккаунтов.

Поддержка английского предусматривается отделением транспорта/типов и использованием стабильных кодов состояний API. Каталог переводов и переключение языка относятся к следующему этапу.
